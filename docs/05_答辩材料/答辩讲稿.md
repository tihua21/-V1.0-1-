## 3. 查元昊｜2:30–3:45｜P5–P6（约 409 字，≈102s，略超）

详细设计先看数据模型。全库 8 个实体，每个实体一个主键 id；8 组关系里 7 组是一对多，会议室和设备是多对多，通过关联表拆成两个一对多。booking 是核心表：user_id、room_id、slot_id 三个外键，加 booking_date 和 start_time、end_time 快照。预约按预置时段下单，但起止时刻要单独存：一是可以直接按半开区间判冲突，二是管理员以后改时段，已有预约的时间不会变。booking_no 在审核通过时才生成，格式 BK 加日期加四位序号。状态 0 到 4：待审核、已预约、已驳回、已取消、已结束；0 和 1 都算有效预约，都要参与冲突检测。状态流转是：提交进 0，管理员通过到 1，驳回进 2，取消进 3，时间结束到 4。改期不修改原记录，而是新记录用 reschedule_from_id 指向原预约，原记录保留到新预约通过。下面请秦瑞祥讲冲突检测和运行验证。

## 4. 秦瑞祥｜3:45–5:00｜P7–P8（约 351 字，≈88s，略超）

这是提交预约与冲突检测时序图。提交后 Controller 校验身份和参数，Service 查会议室状态和有效预约，然后分四条分支：未登录或参数非法返回 400 或 401；会议室停用 409；时段冲突 409，提示已被占用；无冲突写入待审核。判定用半开区间：新开始小于旧结束，并且新结束大于旧开始；首尾相接不算冲突。9 组数据验证：完全重叠、前后重叠、包含、被包含都拒绝；首尾相接、不同会议室、取消后重订都放行，9 组全部符合预期。最后看运行闭环，五张截图：登录、查会议室、看详情、填表单、提交成功到我的预约，管理员在后台审核。三条结论：13 个用例覆盖两个角色；9 组冲突测试 9 比 9 一致；5 个核心页面跑通闭环。总结一句：V1.0 用最小范围跑通了需求、设计、实现和验证的闭环。谢谢大家。

## 可能被追问的 3 个点

1. 为什么用半开区间？闭区间会把 10:00 结束和 10:00 开始的相邻时段判成冲突；半开区间 `[start, end)` 首尾相接不冲突，符合预置时段的实际使用。
2. 为什么状态 0 和 1 都算有效？待审核也要占位，否则同一时段会被重复提交；状态 2、3、4 已释放时段，不再参与冲突检测。
3. 改期为什么不改原记录？原预约保留到新预约审核通过，避免审核期间时段被释放；通过后原记录转"已取消"，原因写"已改期"，历史可追溯。
